# Локальный фундамент

Модуль: инфраструктура и начальная схема аккаунтов, групп, студентов. Контракт: публичный `GET /api/health` проверяет PostgreSQL, возвращает 200 или 503 без внутренних деталей. Границы: `src/`, `scripts/`, `infra/`, `drizzle/`, конфигурация сборки. Авторизация и seed профилей A/B добавлены следующим модулем (см. ниже); остальные таблицы ядра и полноценный интерфейс ещё предстоят; этап 1 MASTER-SPEC пока не принят.

## Запуск

Нужны запущенный Docker Desktop с Linux-контейнерами (или Docker Engine с Compose) и Node.js 24 для генерации локального окружения. Зависимости приложения устанавливаются внутри образа; `npm ci` на хосте нужен только для разработки и тестов.

На Windows запустить Docker Desktop можно командой `docker desktop start`. Выполняйте команды из корня репозитория:

```sh
node scripts/init-env.mjs
node scripts/init-auth-env.mjs
docker compose up -d --build --wait
docker compose --profile tools build seed
docker compose run --rm --no-deps seed
```

Первую команду генерации выполняют только при отсутствии `.env`: существующий файл не перезаписывается. Генераторы создают случайные пароли и ключ авторизации без вывода значений; на POSIX файл создаётся с правами 0600, на Windows доступ определяется ACL папки. Наполнение создаёт два синтетических профиля и демоданные всех реализованных разделов. Логины и пароли находятся в `DEMO_A_*` и `DEMO_B_*` файла `.env`.

Открыть https://localhost/login. Для доверия локальному HTTPS экспортировать корневой сертификат Caddy и установить его в доверенные корневые сертификаты ОС/браузера:

```sh
docker compose cp caddy:/data/caddy/pki/authorities/local/root.crt /tmp/deanery-local-root.crt
curl --cacert /tmp/deanery-local-root.crt https://localhost/api/health
```

Закрытый ключ CA не экспортировать. На Windows сертификат устанавливается в хранилище текущего пользователя. До установки браузер предупреждает о недоверенном сертификате.

На Windows для копии сертификата используйте путь `$env:TEMP/deanery-local-root.crt` вместо `/tmp/deanery-local-root.crt`.

Повторный запуск и остановка с сохранением данных:

```sh
docker compose up -d --wait
docker compose ps
docker compose stop
```

Скрипты `*.sh` закреплены в Git с окончаниями строк LF, чтобы инициализация PostgreSQL работала и после получения исходников на Windows с `core.autocrlf=true`.

```sh
npm ci
npm test
npm run typecheck
npm run build
docker compose run --rm migrate
```

Миграции выполняются перед приложением и повторно не применяются. `npm run db:generate` создаёт следующую миграцию из Drizzle-схемы. Проверять SQL перед применением. БД не публикует порт на хост; миграционный контейнер получает только URL владельца, приложение — только URL ограниченной роли. `docker compose down` сохраняет данные; не использовать `down -v` для остановки рабочего стенда.

### Доступ с телефона в локальной сети

В `.env` задайте `SITE_ADDRESS` локальным IPv4 компьютера, `APP_ORIGIN=https://<IPv4>`, `BIND_ADDRESS=<IPv4>` и `LOCAL_APP_ORIGIN=https://localhost`, затем выполните `docker compose --profile local-dual up -d --wait`. Телефон и компьютер должны находиться в одной сети; брандмауэр должен разрешать входящие TCP 80 и 443. Откройте на телефоне `https://<IPv4>/login`, а на компьютере — `https://localhost/login`. Это разные адреса и отдельные сессии. При смене IPv4 обновите настройки и пересоздайте контейнеры той же командой. Профиль `local-dual` и `LOCAL_APP_ORIGIN` предназначены только для локальной разработки; на публичном сервере их не включают.

Caddy выдаёт для частного IPv4 сертификат локального центра. Для доверенного HTTPS экспортируйте только корневой сертификат командой выше, безопасно перенесите его на телефон и установите доверие к нему в настройках устройства. На iOS после установки профиля дополнительно включите полное доверие к сертификату; на Android порядок зависит от версии и браузера. Не передавайте закрытый ключ центра сертификации. Удалите доверие к локальному корню, когда оно больше не нужно. Реальный доступ зависит также от изоляции клиентов Wi-Fi и сетевых настроек хоста/WSL.

## Будущий сервер

Использовать тот же Dockerfile и Compose. Создать новые секреты на сервере, задать `SITE_ADDRESS` реальным доменом, `APP_ORIGIN=https://домен`, `BIND_ADDRESS=0.0.0.0`. Направить DNS на сервер, открыть 80/443; Caddy выпустит публичный сертификат. Приложение и PostgreSQL доступны только внутри Compose. Локальный сертификат на сервер не переносится. При смене паролей существующей БД требуется отдельная ротация ролей: init-скрипт работает только на пустом томе.

Перед публикацией: завершить авторизацию и матрицу A/B, перепроверить закреплённые digest образов, перепроверить обновления безопасности, настроить зашифрованные внешние копии без сессий, восстановление и мониторинг по MASTER-SPEC. Сейчас этого ещё нет. Локальная техническая страница использует системный шрифт; Literata/Manrope и shadcn входят в будущий модуль интерфейса.

Standalone-упаковка сверена с [документацией Next.js](https://nextjs.org/docs/app/api-reference/config/next-config-js/output).

## Авторизация и синтетические профили

```sh
node scripts/init-auth-env.mjs
docker compose build app migrate seed
docker compose up -d
docker compose run --rm seed
npx playwright test
```

Генератор добавляет отсутствующие настройки в `.env`, не печатает и не меняет существующие секреты. Локальные логины и пароли находятся в полях `DEMO_A_*` и `DEMO_B_*` этого файла: открыть его локально в редакторе. Не копировать значения в журнал или Git. Открыть https://localhost/login. Seed создаёт только профили; повтор сохраняет действующие пароли и данные. Остальные данные ядра будут добавлены следующими миграциями.

`AUTH_SECRET` используется для HMAC CSRF и корзин ограничения входа; при смене ключа открытые формы должны запросить новый CSRF. В production разрешён доступ к приложению только через Caddy, который заменяет `X-Real-IP`; публикация порта приложения нарушит модель доверия лимитов. Вход и выход работают только с HTTPS Origin из `APP_ORIGIN`.

На отдельном стенде с синтетическими данными можно включить `ENABLE_DEMO_LOGIN=true`. Если доступен синтетический профиль 3, на странице входа появится кнопка «Войти тестовым аккаунтом». После смены логина этого профиля задайте актуальный логин в серверной переменной `DEMO_MOBILE_LOGIN`. Профили A и B входят по своим учётным данным. На стендах с отдельными учётными записями оставьте настройку выключенной.

Основной seed заполняет существующий локальный профиль `test3` в группе «Маяк-21». Для создания такого профиля на чистой базе задайте в серверном окружении `DEMO_MOBILE_PASSWORD` длиной от 16 символов и запустите обычный seed. У уже существующего профиля пароль сохраняется.

Текущая область приёмки: `/api/v1/csrf`, `/api/v1/session/login`, `/api/v1/session/logout`, `/api/v1/me`, `/login`, `/profile`. Проверки полного ядра, общих объектов группы, шрифтов, тем и резервного восстановления остаются отдельной работой. Браузерные тесты отключают трассировку и запись видео, чтобы не сохранять вводимые пароли.

В текущей WSL-среде Chromium потребовал дополнительные библиотеки. Для выполненного прогона они распакованы в `/tmp` (после очистки временных файлов путь недействителен):

```sh
LD_LIBRARY_PATH=/tmp/deanery-browser-libs/root/usr/lib/x86_64-linux-gnu npx playwright test
```

На обычной машине установить зависимости через `npx playwright install --with-deps chromium`. Частые повторные прогоны используют общий локальный IP и могут закономерно получить 429: выдержать 15 минут. Тесты нельзя направлять на публичный стенд. Миграционный запуск проверяет возрастающие метки времени журнала: это защищает от пропуска новых миграций при сдвиге системных часов.

## Расписание и учёба

После обновления выполнить:

```sh
docker compose build app migrate seed
docker compose up -d --wait
docker compose run --rm seed
```

Команда seed добавляет учебный план, оценки, пары, редакции, события сессии и сроки к двум демопрофилям. Повторное наполнение сохраняет существующие учётные данные и записи. Занятия заполнены до 28 ноября 2026 включительно. Блоки «Сегодня» берут дату и время МСК с сервера.

Для контрольного сценария из MASTER-SPEC и учебных тестов задать 17 ноября, 09:00 МСК на localhost:

```sh
DEMO_ACADEMIC_NOW=2026-11-17T06:00:00Z docker compose up -d --wait
npx playwright test tests/e2e/academics.spec.ts
docker compose up -d --wait
```

Последняя команда восстанавливает реальные часы, если переменная не задана в `.env`. Вне `https://localhost` сервер всегда использует реальные часы. Для нового раздела доступны `/schedule`, `/study`, их карточки и три связанных блока на `/today`. Ближайший срок на главной учитывает и сроки, связанные с заявками. Уведомления о сроках доступны во входящих.

## Заявки и справки

После сборки и повторного наполнения доступны два готовых образца справок. В аккаунте B также есть заявление, ожидающее уточнения. Повтор seed сохраняет пользовательские заявки и ответы на уточнения.

На `/requests` можно выбрать услугу, проверить реквизиты перед отправкой и открыть карточку с историей. Миграция добавляет каталог форм и реестр синтетических начислений. После миграции повторите seed для заполнения реестра. Для проверки справки о начислении выберите в аккаунте A академическую стипендию за сентябрь–октябрь 2026 года, в B — социальную за октябрь 2026 года. Если за запрошенный период нет начислений выбранного вида, в карточке появится причина отказа.

Заявка переходит в работу примерно через 20 секунд, следующий статус появляется примерно через минуту после подачи. Владельцу готовой справки доступен образец PDF. Для заявлений на индивидуальный график, общежитие и пропуск финальный демонстрационный статус «Зарегистрирована» подтверждает приём заявления. Сервер проверяет ожидающие заявки раз в 5 секунд. Таймер, реквизиты и история сохраняются в PostgreSQL. Для обновления каталога помощника подготовлены новые редакции УЧ-02, ОТ-01 и СС-01. Порядок сверки и публикации описан в [инструкции по документам](../documents/README.md).

Сквозной тест изменяет состояние фикстур. Запускайте его на отдельном временном проекте Compose. Образы нужно предварительно собрать командой `docker compose build app migrate seed`. Если основной проект Compose называется иначе, задайте `REQUESTS_TEST_IMAGE_PREFIX` его именем.

```sh
export APP_ORIGIN=https://localhost:8443
docker compose -p mgimo-requests-check -f compose.yaml -f tests/compose.requests.yaml up -d --wait --no-build --scale app=2
docker compose -p mgimo-requests-check -f compose.yaml -f tests/compose.requests.yaml run --rm --no-deps seed
REQUESTS_TEST_ORIGIN=https://localhost:8443 npx playwright test tests/e2e/requests.spec.ts
docker compose -p mgimo-requests-check -f compose.yaml -f tests/compose.requests.yaml down -v
unset APP_ORIGIN
```

Тест использует порт 8443 и создаёт отдельный том PostgreSQL. Последняя команда Compose удаляет том именно временного проекта.

## Входящие

После обновления выполните `docker compose build app migrate seed`, `docker compose up -d --wait` и `docker compose run --rm --no-deps seed`. Новых таблиц для этого шага нет. Наполнение добавляет вымышленные объявления, изменения расписания и сроки с устойчивыми ключами, сохраняя отметки прочтения.

Раздел `/inbox` показывает активные сроки по дате, затем свежие уведомления. Фильтры «Все», «Важное» и «Дедлайны» сохраняются в URL. Счётчик отражает все доступные непрочитанные сообщения. После открытия карточки отметка сохраняется в базе и видна после повторного входа. Перенос с аудиторией 408 в контрольном сценарии появляется 17 ноября, 09:00 МСК. Обычный стенд использует реальные часы.

Сквозной тест меняет состояние фикстур, поэтому запустите отдельный стенд на порту 8443 с ранее собранными образами:

```sh
APP_ORIGIN=https://localhost:8443 DEMO_ACADEMIC_NOW=2026-11-17T06:00:00Z docker compose -p mgimo-inbox-check -f compose.yaml -f tests/compose.requests.yaml up -d --wait --no-build
APP_ORIGIN=https://localhost:8443 docker compose -p mgimo-inbox-check -f compose.yaml -f tests/compose.requests.yaml run --rm --no-deps seed
INBOX_TEST_ORIGIN=https://localhost:8443 npx playwright test tests/e2e/inbox.spec.ts
APP_ORIGIN=https://localhost:8443 docker compose -p mgimo-inbox-check -f compose.yaml -f tests/compose.requests.yaml down -v
```

## Qwen на закрытом тестовом стенде

Включайте интеграцию только на закрытом стенде с синтетическими вопросами. Оператор Tesla выдаёт отдельный SSH-ключ пользователя `modelonly`. Для моста пользователь должен иметь право выполнить `python3` и прочитать ключ шлюза через `sudo -n /usr/bin/cat /etc/tesla-model-gateway/api-key`. Используйте запись ключа сервера, сверенную по доверенному каналу. Файлы остаются вне репозитория.

Серверные файлы и загруженные администратором документы считаются доверенными; студенты их не загружают. Перед публикацией после `prepare` сверяйте оригинальный PDF, `document.md` и фрагменты `index.json` со страницами источника, включая текст слоя PDF и OCR. Это проверка корректности извлечения и содержания. При расхождении исправьте источник и подготовьте новую редакцию; публикуйте проверенную редакцию. При смене модели или её инструкций повторите проверки помощника на тех же синтетических сценариях.

Добавьте в локальный `.env` абсолютные пути, доступные пользователю контейнера (UID 1000). У закрытого ключа должны быть права `0600`.

```dotenv
COMPOSE_FILE=compose.yaml:compose.qwen.yaml
TESLA_QWEN_SSH_KEY=/home/operator/.ssh/mgimo-vibecode-qwen
TESLA_QWEN_KNOWN_HOSTS=/home/operator/.ssh/known_hosts
ASSISTANT_QWEN_MODEL=deanery-compare-36-q4-4k
```

```sh
docker compose up -d --build --wait
docker compose ps app qwen-bridge
```

Сервис `qwen-bridge` запускается вместе со стендом. У него нет опубликованных портов. Приложение использует Unix-сокет в общем томе, а мост создаёт отдельное SSH-соединение на каждый запрос с обязательной проверкой ключа сервера. После обрыва следующий запрос автоматически открывает новое соединение. Docker перезапускает сервис после сбоя и перезапуска Docker. Ключ API читается на Tesla и не нужен в локальном окружении.

Тег `deanery-compare-36-q4-4k` на Tesla содержит Qwen3.6 27B Q4_K_M с `num_ctx=4096`. Адаптер использует температуру 0, отключённый thinking и лимит ответа 256 токенов. При открытии кабинета после входа мост в фоне прогревает тот же тег через `127.0.0.1:11434/api/generate` на Tesla. Локальный Ollama API должен быть доступен пользователю моста. Вызов передаёт только тег модели и параметры загрузки. При тайм-ауте установки SSH мост делает до двух повторов. Возврат во вкладку и взаимодействие с кабинетом продлевают время загрузки, максимум раз в минуту. Для обычных ответов оставьте стандартный `OLLAMA_KEEP_ALIVE=5m` или убедитесь, что шлюз задаёт тот же срок.

Для проверки начните с выгруженной модели на отдельном стенде. Войдите в кабинет, оставаясь на главной, и проверьте на Tesla тег и колонку `PROCESSOR`.

```sh
ollama ps
```

Спросите «Как продлить библиотечный абонемент?» и проверьте отметку Qwen под ответом. Закройте вкладки кабинета и повторите `ollama ps` через пять минут после последнего обращения к модели. Тег должен исчезнуть, если на Tesla его больше никто не использует. Если открыть чат сразу после входа, холодная загрузка ещё может идти и первый запрос может исчерпать бюджет в 10 секунд. При отсутствии моста или сбое модели кабинет автоматически использует каталог.

Для разового запуска без Qwen используйте `docker compose -f compose.yaml up -d --wait`. Для постоянного отключения сначала выполните `docker compose stop qwen-bridge`, затем удалите строку `COMPOSE_FILE` из `.env` и обновите контейнер приложения. База и документы не затрагиваются. Для прямого подключения без Compose остаются настройки `ASSISTANT_QWEN_BASE_URL`, `ASSISTANT_QWEN_MODEL` и `ASSISTANT_QWEN_API_KEY`.

## Проверка расширенных данных интерфейса

После применения миграций общее наполнение `npm run db:seed` добавляет синтетические внеучебные события, преподавателей, работы, услуги и занятия физкультурой. Команды `npm run db:seed-extracurricular` и `npm run db:seed-interface` запускают эти части отдельно. Повторное наполнение сохраняет существующие результаты и записи.

`tests/e2e/interface-data.spec.ts` проверяет доступ к работам, календарю и расписанию преподавателя. Для проверки конкурентной записи и формы заявки укажите `INTERFACE_TEST_DATABASE_URL` для отдельной тестовой БД и `PLAYWRIGHT_BASE_URL` для связанного с ней HTTPS-приложения. Эти сценарии создают и изменяют синтетические данные.

## Проверка диалогов помощника

На локальном стенде с синтетическими аккаунтами A и B и включённым Qwen:

```sh
npx vitest run tests/assistant*.test.ts
npx playwright test tests/e2e/assistant-schedule.spec.ts
```

Первый прогон проверяет правила и опечатки, включая ошибки, сгенерированные удалением каждого символа слова. Второй обращается к работающему приложению и передаёт контекст между репликами. Часть вопросов требует `processing: "qwen"`, поэтому ответ из каталога при недоступном шлюзе не засчитывается как проверка модели. Эти проверки API не запускают браузер и не изменяют учебные данные.

Проверка `/prototype#assistant` запускается командой `node scripts/design/verify-chat.mjs` в Chrome на отдельном HTTPS-стенде с аккаунтами A/B. `PROTOTYPE_URL` указывает полный адрес `/prototype`, а `PROTOTYPE_LIVE_QWEN=1` добавляет проверку ответа живой модели после входа. Сценарий входит и выходит тестовыми аккаунтами и сохраняет снимки в `test-results/interface`.

## Изоляция студентов одной группы

Для локального прогона матрицы используйте `bash scripts/check-security-matrix.sh` после сборки образов `docker compose build app migrate seed`. Скрипт создаёт отдельный проект Compose с приложением на порту 8443 и PostgreSQL на порту 55432, доступных только через loopback, и удаляет его тома при завершении. Для браузерных сценариев потребуется установленный Chromium Playwright. Между наборами скрипт сбрасывает лимиты входа только в своей синтетической базе. В конце он применяет фикстуру общей группы и запускает соответствующую проверку.

На отдельном синтетическом стенде после миграций и seed выполните `tests/fixtures/same-group-isolation.sql` под ролью владельца БД. Скрипт изменяет и добавляет фикстуры и предназначен для свежей отдельной тестовой базы. Затем запустите `SAME_GROUP_TEST_ORIGIN=https://localhost:8443 npx playwright test tests/e2e/same-group-isolation.spec.ts`. Для повторного запуска подготовьте новую тестовую базу.

## Локальная оценка детектора инъекций

Скрипт `scripts/evaluate-prompt-guard.py` проводит небольшой диагностический прогон синтетических вопросов. Для запуска нужны Python, `numpy`, `onnxruntime`, `tokenizers` и скачанная директория `onnx` модели `viavoice/mdeberta-ru-prompt-injection`. Укажите её через `GUARD_ONNX_DIR`. Эксперимент использует CPU и не подключён к приложению. Небольшой набор предназначен для проверки запуска и отдельных сбоев. Порог и пригодность для эксплуатации определяются на независимой расширенной выборке.

Для воспроизведения результатов используйте ревизию `8e0fdb567ad0d1ddac0c9c1819b182204db26867`. На 75 тестовых вопросах при пороге 0,99 модель пометила 27 из 35 подозрительных запросов и один из 40 обычных. Некоторые подозрительные примеры проверяют реакцию на запрос чужих данных, поэтому эта доля охватывает более широкий сценарий, чем обнаружение инъекций. Ошибка на обычном вопросе о заявке и пропуски не обосновывают включение блокировки. Скрипт пригоден для повторной оценки новых редакций модели.

### Парный прогон Qwen и локального каталога

Фикстура `tests/fixtures/guard-questions.json` содержит 122 обычные синтетические реплики, включая уточнения, и восемь контрольных запросов. На отдельном закрытом стенде порты 8443 и 8444 ведут к экземплярам с Qwen и с каталогом. Они используют одну синтетическую БД, фиксированное академическое время и один каталог. Для очередного уточнения в обе ветки передаётся контекст предыдущего ответа Qwen. Скрипт отмечает изменение видимого ответа и сохраняет пары в JSONL для ручной проверки.

Соберите образы приложения, наполнения, миграций, моста и импорта документов заранее. Для воспроизведения задайте настройки моста из раздела выше и выполните:

```bash
export SITE_ADDRESS=localhost APP_ORIGIN=https://localhost:8443 DEMO_ACADEMIC_NOW=2026-11-20T06:00:00Z
stand=(docker compose -p deanery-guard-check -f compose.yaml -f compose.qwen.yaml -f tests/compose.requests.yaml -f tests/compose.guard-evaluation.yaml)
"${stand[@]}" up -d --wait --no-build
"${stand[@]}" run --rm --no-deps seed
"${stand[@]}" run --rm --no-deps document-import publish study-certificates 68bbb163fbc760ac0df6f1ca4c1ef30386966a2c9d654d1cb86d18001007d58c
"${stand[@]}" run --rm --no-deps document-import publish library-loans 5a243c2333908213b35b926e6c777e24b24c80427ae50a4ce1c966889eb58b7e
node scripts/replay-guard-questions.mjs /tmp/deanery-guard-replay.jsonl
GUARD_ONNX_DIR=/path/to/onnx python scripts/evaluate-prompt-guard.py /tmp/deanery-guard-replay.jsonl 0.9993
"${stand[@]}" down -v
```

Последняя команда удаляет только тома временного проекта. Для повторного прогона выберите новый путь JSONL. Селектор `processing: qwen` подтверждает влияние принятого ответа модели. Вызов Qwen с отброшенным результатом может иметь другую отметку. Список изменившихся ответов требует ручной оценки по цели запроса. Для другой бинарной ONNX-модели должны совпадать формат входов и порядок классов, где индекс 1 означает подозрительный ввод. Длину входа можно задать через `GUARD_MAX_TOKENS`.

При заранее выбранном пороге 0,9993 mDeBERTa RU пометила 2 из 122 обычных реплик и 4 из 8 контрольных запросов. Среди 99 обычных реплик с влиянием Qwen одна отметка изменила бы видимый ответ о справке, заменив краткий ответ выдержками. Среди пяти контрольных запросов с влиянием Qwen в одном случае каталог дал бы уточнение вместо несвязанного расписания. Блокировка не включена. Официальное хранилище Meta Prompt Guard 2 86M вернуло 401 и требует доступа к весам через Hugging Face.

Для официальной модели Meta укажите папку скачанной ревизии в `GUARD_SAFETENSORS_DIR`. Для этого варианта нужны CPU-версии PyTorch и Transformers. Скрипт читает локальные Safetensors с отключённым исполнением кода из репозитория модели. Порогов можно передать несколько, оценки вычисляются один раз.

```bash
GUARD_SAFETENSORS_DIR=/path/to/official/meta/snapshot HF_HUB_OFFLINE=1 \
  python scripts/evaluate-prompt-guard.py /tmp/deanery-guard-replay.jsonl 0.5 0.9 0.99 0.9993
```

Официальная ревизия Meta `a8ded8e697ce7c355e395a0df51f94adb4a2fd27` на том же наборе дала 5 ложных отметок из 122 обычных реплик при пороге 0,5 и 3 при 0,9 и 0,99. При 0,9993 ложных отметок было 0. Ни один из восьми контрольных запросов не отмечен при проверенных порогах. Этот набор не показал пользы от применения Meta в помощнике.
