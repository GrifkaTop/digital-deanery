# Будущий перенос на сервер с Qwen

Подготовлено 21 ноября 2026. Сайт пока не переносился; команды ниже выполняются только при фактическом переносе. Сервер, DNS, рабочие контейнеры и модель в рамках подготовки не менялись.

Границы: Docker Compose, серверное окружение, копия PostgreSQL и опубликованных документов, подключение существующего Qwen, проверка и откат. Приложение и модель остаются отдельными процессами: Next.js не использует GPU и не запускает Ollama. Основа — §8 и §9 [MASTER-SPEC](MASTER-SPEC.md). Yandex Cloud / Selectel остаются планом публичного размещения; совместный сервер — подготовленный вариант, требующий проверки перед запуском.

## Что уже подготовлено

- `scripts/init-server-env.mjs` создаёт отдельный файл с новыми случайными секретами и правами `0600`, отказывается перезаписывать существующий. Локальный `.env` сохраняется.
- `scripts/backup-server.sh` создаёт GPG-зашифрованный пакет с дампом PostgreSQL без строк `public.sessions`, `documents/versions`, контрольными суммами и номером исходного коммита. Пароли окружения, SSH-ключи и TLS-ключи в него не входят. При сбое готовый файл не появляется.
- `compose.yaml` уже содержит приложение, миграции, PostgreSQL 16 и Caddy; наружу выходят только 80/443. Файл для сервера отдельно дублировать не требуется: домен и привязка портов задаются окружением.
- `compose.qwen.yaml` добавляет необязательный SSH-мост. Его адрес, порт и пользователь настраиваются. Старые значения по умолчанию сохранены. Для обращения к самому Linux-хосту добавлено имя `host.docker.internal`.

## Перед переносом заполнить карточку

| Параметр | Нужно определить |
| --- | --- |
| Сервер | Адрес, оператор, SSH-доступ, ОС, архитектура CPU |
| Ресурсы | Свободные RAM/CPU/диск при загруженной Qwen; место для сборки, БД и копий |
| HTTPS | Собственный домен, доступ к DNS, IPv4; AAAA только при рабочем IPv6 |
| Порты | Свободны ли 80/443; какие сервисы уже используют reverse proxy |
| Qwen | Реальный SSH-порт и ключ сервера; доступен ли из Docker локальный SSH; модель и шлюз |
| Данные | Исходный Compose project, путь env и хранилища документов, выбранный Git-коммит |
| Копия | GPG fingerprint получателя, внешний каталог хранения, доступ к приватному ключу восстановления |
| Переключение | Окно обслуживания, ответственный, прежнее значение DNS и измеренный TTL |

Проверка сервера до изменений: `docker version`, `docker compose version`, `free -h`, `df -h`, `ss -lnt`. Не останавливать существующую Qwen ради сайта. Сборку лучше заранее выполнить на совместимой машине, если RAM занята моделью. Версии/обновления безопасности закреплённых образов проверяются перед релизом.

Если 80/443 заняты существующим proxy, сначала согласовать отдельный hostname и маршрутизацию с оператором. Приведённый далее путь рассчитан на свободные 80/443; он не подходит для запуска второго Caddy поверх действующего. Не менять существующий proxy вслепую.

## 1. Подготовить релиз и окружение

На исходной машине закончить необходимые изменения, проверки и сохранить их в Git. Перед выбором релиза проверить `git status --short`: архив коммита не содержит незакоммиченных файлов. Не отправлять весь рабочий каталог вместе с `.env`, ключами или копиями.

Исходники получить на сервере из закрытого репозитория с доступом только на чтение либо передать архив выбранного коммита:

```bash
git archive --format=tar.gz --output=/tmp/deanery-source.tar.gz COMMIT
```

`COMMIT` — выбранный проверенный SHA. Опубликованные PDF находятся вне Git и переносятся с копией данных. Убедиться, что релиз содержит весь актуальный код и миграции, соответствующие копии. При передаче готовых Docker-образов нужны образы целей `runner` и `migrate` и совпадающая архитектура; нельзя ограничиться одним образом приложения.

В отдельном каталоге релиза на сервере (пример `/srv/deanery`) при наличии Node.js 24:

```bash
node scripts/init-server-env.mjs cabinet.example.org
```

Здесь и далее `cabinet.example.org` заменить собственным доменом. Если Node.js на хосте отсутствует, сгенерировать `.env.server` на доверенной машине с Node.js 24 и передать отдельно по SSH. Не запускать локальные `init-env.mjs` / `init-auth-env.mjs` поверх серверных настроек.

В `.env.server` проверить `SITE_ADDRESS`, `APP_ORIGIN=https://домен`, `BIND_ADDRESS=0.0.0.0`, путь `ASSISTANT_DOCUMENTS_DIR`. `LOCAL_APP_ORIGIN` и `DEMO_ACADEMIC_NOW` оставить пустыми; `ENABLE_DEMO_LOGIN=false`. Права файла — `0600`, каталог доступен только оператору. Никогда не прикладывать содержимое env или полный вывод `docker compose config` к отчёту.

Все следующие серверные команды запускаются из каталога релиза. Функция выбирает отдельный проект и env, игнорируя локальный `COMPOSE_FILE`:

```bash
dc() { docker compose --env-file .env.server -p deanery-server -f compose.yaml "$@"; }
dc config --quiet
dc build app migrate seed
```

Имя проекта `deanery-server` сохранять между релизами: от него зависят имена томов. На этом этапе контейнеры ещё не запускаются. Если в shell экспортированы одноимённые переменные, они имеют приоритет над env-файлом: выполнять команды из чистой операторской сессии.

## 2. Снять копию исходного сайта

Нужны Bash, GNU coreutils/tar, GnuPG, Git и Docker Compose. В GPG оператора заранее импортирован и проверен публичный ключ получателя; приватный ключ хранится отдельно и доступен для репетиции восстановления. Передавать пароль ключа через командную строку нельзя.

Для финального переноса сначала остановить приём запросов и приложение на исходной площадке, сохранив БД. Использовать действительные env/project/compose-файлы источника. Пример для обычного локального проекта:

```bash
docker compose --env-file .env -p SOURCE_PROJECT -f compose.yaml stop caddy app
bash scripts/backup-server.sh .env SOURCE_PROJECT ./documents /tmp/deanery-final.tar.gpg GPG_FINGERPRINT
```

Заменить `SOURCE_PROJECT` и `GPG_FINGERPRINT`. Не выполнять эти команды сейчас. Путь `./documents` должен совпадать с фактическим `ASSISTANT_DOCUMENTS_DIR` источника. На время копии запретить публикацию/отзыв/удаление версий документов и запуск миграций/seed; обычный `pg_dump` согласован для БД, но файловое хранилище не входит в его транзакцию. Для периодической копии остановка сайта не обязательна; импорт документов всё равно координировать.

Передать шифрованную копию по SSH на сервер и сохранить ещё одну вне него. `.env` источника хранить отдельно в зашифрованном хранилище оператора. Не переносить старые сессионные cookies. Для восстановленной БД демологины и пароли остаются прежними: сгенерированные в новом env значения не меняют хеши существующих аккаунтов. Включить корректные доступы в отдельную закрытую карточку оператора.

## 3. Восстановить в новую пустую БД

Сначала провести репетицию на отдельном проекте без публичных портов. Восстанавливать только доверенную копию в **пустую** БД, до запуска приложения и миграций. Не выполнять `down -v` или `pg_restore --clean` на работающем проекте.

```bash
umask 077
mkdir -m 700 /tmp/deanery-restore
gpg --output /tmp/deanery-restore/payload.tar --decrypt /tmp/deanery-final.tar.gpg
tar -xf /tmp/deanery-restore/payload.tar -C /tmp/deanery-restore
(cd /tmp/deanery-restore && sha256sum --check SHA256SUMS)
dc up -d --wait db
dc exec -T db pg_restore --list < /tmp/deanery-restore/database.dump > /tmp/deanery-restore/contents.txt
dc exec -T db pg_restore -U deanery_owner -d deanery --no-owner --no-acl --exit-on-error --single-transaction < /tmp/deanery-restore/database.dump
```

Если восстановление не прошло — не продолжать запуск. Выяснить причину; повторять восстановление только в новой пустой БД. Роли и пароли не входят в дамп: `infra/init-db.sh` создаёт их из нового env при первом запуске пустого тома. Восстановление от имени владельца использует его default privileges; явно закрепить доступ приложения и проверить отсутствие сессий:

```bash
dc exec -T db psql -U deanery_owner -d deanery -v ON_ERROR_STOP=1 <<'SQL'
GRANT USAGE ON SCHEMA public TO deanery_app;
GRANT SELECT, INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO deanery_app;
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO deanery_app;
SELECT count(*) AS restored_sessions_must_be_zero FROM public.sessions;
SQL
```

Результат счётчика должен быть `0`. Скопировать `/tmp/deanery-restore/documents/versions` в `ASSISTANT_DOCUMENTS_DIR/versions` (по умолчанию `./documents/versions`). Каталоги должны быть доступны контейнерному UID 1000 на чтение/проход, файлы — на чтение. Не делать PDF публичной раздачей proxy: доступ остаётся через авторизованный API. Затем:

```bash
dc run --rm migrate
```

Для переноса существующих данных **не запускать seed по привычке**: он обновляет синтетические эталоны. Если обновление наполнения требуется конкретному релизу, выполнить его отдельно после копии и проверки. Для полностью нового пустого стенда вместо восстановления: создать `documents/versions`, выполнить миграции и `dc run --rm seed`; публикации PDF импортировать по `documents/README.md`.

## 4. Qwen на этом же сервере (необязательно)

Для первого запуска кабинета Qwen не требуется. Публичное включение модели остаётся ограничено §9 MASTER-SPEC; до решения по обработке свободного вопроса использовать её только на закрытом стенде с синтетическими вопросами. Не публиковать наружу порты Ollama и шлюза и не запускать вторую копию модели.

Сохраняется существующий путь: приложение → Unix-сокет → SSH-мост → локальный защищённый шлюз Qwen. API-ключ шлюза остаётся на сервере модели. Для совместного размещения `.env.server` уже предлагает `TESLA_QWEN_SSH_HOST=host.docker.internal`. Это адрес хоста из контейнера, а не loopback контейнера. `http://host.docker.internal:8081/v1` как прямой URL не использовать: адаптер разрешает незашифрованный HTTP только на loopback.

Оператор должен подтвердить реальный `TESLA_QWEN_SSH_PORT` (прежнее значение 8022 — значение текущего удалённого подключения, на самом сервере порт может отличаться), пользователя `modelonly`, доступность SSH из Docker и существование модели `deanery-compare-36-q4-4k`. Для ответов нужны Python 3, локальный `127.0.0.1:8081/v1/chat/completions` и право `sudo -n /usr/bin/cat /etc/tesla-model-gateway/api-key`. Для прогрева при входе мосту нужен локальный `127.0.0.1:11434/api/generate`. Проверка загрузки и освобождения видеопамяти описана в [инструкции стенда](local-development.md#qwen-на-закрытом-тестовом-стенде).

В `TESLA_QWEN_SSH_KEY` указать абсолютный путь отдельного ключа, в `TESLA_QWEN_KNOWN_HOSTS` — файла с проверенным ключом сервера. Запись должна соответствовать **имени и порту из контейнера**, например `[host.docker.internal]:8022`, с ключом, сверенным оператором по доверенному каналу. Не отключать `StrictHostKeyChecking` и не считать результат `ssh-keyscan` самостоятельной проверкой. Файлы должны читаться UID 1000 моста; приватный ключ — только владельцем, вне репозитория.

Для закрытого стенда определить другую функцию:

```bash
dq() { docker compose --env-file .env.server -p deanery-server -f compose.yaml -f compose.qwen.yaml "$@"; }
dq config --quiet
dq build app migrate qwen-bridge
dq up -d --wait
```

После включения моста все команды запуска выполнять с обоими compose-файлами. Проверить синтетический вопрос после входа и `processing=qwen` в ответе API: один health-check кабинета не подтверждает работу модели. При отказе/таймауте должен работать поиск каталога. Для отключения: `dq stop qwen-bridge`, затем `dc up -d --wait`; не удалять том БД.

## 5. Проверка и переключение

Без Qwen: `dc up -d --wait`. Для выпуска сертификата Caddy домен должен разрешаться на сервер, 80/443 — быть доступны. До смены основного DNS провести закрытую репетицию на отдельном hostname с HTTPS; не отключать Secure-cookie ради HTTP.

Проверить `https://домен/api/health`, обычный вход A/B и полный сценарий из MASTER-SPEC: профиль, расписание, PDF/iCalendar, заявка и её сохранение после повторного входа, прочтение, прямые чужие URL (404), выход, другая вкладка и история браузера. Обе темы от 360 px. Сквозные тесты, создающие фикстуры, запускать на отдельной базе.

Только после успешной репетиции: закрыть запись на источнике, сделать финальную копию, восстановить её на цели, проверить данные и переключить DNS. Пока DNS обновляется, источник не должен принимать изменения. Два независимых пишущих экземпляра с разными БД не допускаются.

Проверить ссылку из домашней и мобильной сети РФ без VPN, в одной из них подать заявку и скачать PDF. Записать время, устройство, оператора, возраст финальной копии и время восстановления. Проверить отсутствие опубликованных портов 3000/5432/8081/11434, резервное хранение и доступность модели для закрытого режима.

После проверки безопасно удалить расшифрованную временную копию. Настроить по §8 ежечасное выполнение backup-скрипта, отправку шифрованного результата на другую площадку и оповещение при пропуске/ошибке; эти внешние задания **не устанавливаются** подготовительными скриптами. До 28 ноября контролировать HTTPS, диск, здоровье БД, модель, копии и оплату инфраструктуры.

## Откат

До открытия записи на новой площадке можно вернуть DNS и запустить прежние `app`/`caddy` с прежним env. Источник до этого хранить остановленным, с целыми томами и соответствующим релизом.

Если новая площадка уже принимала заявки/прочтение, сначала закрыть её запись, сделать свежую копию и восстановить её на прежней площадке с совместимым кодом. Простое включение старой БД потеряет новые изменения. Обратные миграции автоматически не выполняются; восстановление копии и выбранного релиза репетируется отдельно. Зафиксировать фактическое время и проверку A/B после отката.
